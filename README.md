# Ordo Panel — панель для переписки с клиентами через Telegram

Веб-панель, через которую несколько сотрудников одновременно ведут переписку с клиентами.
Клиенты пишут в Telegram-бота, сотрудники отвечают им из браузера.

**Панель:** https://ordo-panel.vercel.app
**Бот:** @ordo_damir_support_bot

Учётные записи для проверки:
- `staff1@example.com`
- `staff2@example.com`

(пароли передаются отдельно)

---

## 1. Устройство системы

```
Клиент в Telegram
      ↓ пишет боту
Telegram Bot API
      ↓ webhook (POST + секретный токен в заголовке)
/api/telegram/webhook  ←  Vercel (регион sin1, Сингапур)
      ↓ сохраняет сообщение, перезаливает файлы
Supabase: PostgreSQL + Storage
      ↓ Realtime (websocket)
Панель в браузере у всех сотрудников — обновляется без перезагрузки
      ↓ сотрудник отвечает
/api/messages/send → Telegram Bot API → клиент
```

**Способ получения сообщений: webhook**, не long polling. Причина: проект развёрнут на Vercel,
где нет постоянно работающего процесса — функции запускаются по запросу. Long polling требовал бы
отдельный всегда включённый сервер, что для этого хостинга не подходит.

**Почему файлы перезаливаются.** Telegram отдаёт файлы по временным ссылкам с ограниченным сроком
жизни. Если хранить только эти ссылки, через некоторое время вложения перестанут открываться.
Поэтому при получении файла он сразу скачивается и кладётся в Supabase Storage — оттуда он
доступен и через месяц.

**Защита от дублей.** Telegram повторяет доставку, если не получил подтверждение вовремя.
Перед сохранением проверяется `telegram_update_id` — если такое обновление уже обработано,
сообщение не создаётся повторно.

**Стек:** Next.js 14 (App Router), TypeScript, Supabase (PostgreSQL + Auth + Storage + Realtime),
Vercel. Интерфейс написан без UI-библиотек — на React с инлайновыми стилями и общими CSS-переменными.

## 2. Как запустить у себя

1. `npm install`
2. Создать проект в Supabase, выполнить `supabase/schema.sql` в SQL Editor
3. Там же выполнить дополнительные миграции (см. ниже)
4. В Supabase → Authentication → Users создать сотрудников, для каждого добавить строку
   в таблицу `staff_profiles` (id пользователя + имя)
5. Скопировать `.env.example` → `.env.local`, заполнить своими ключами
6. `npm run dev` — локально, либо задеплоить на Vercel с теми же переменными окружения
7. Подключить бота: открыть в браузере ссылку из `setup-webhook.md`

### Переменные окружения

| Переменная | Где взять |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Settings → Data API |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase → Settings → API Keys → Legacy |
| `SUPABASE_SERVICE_ROLE_KEY` | там же (секретный, только на сервере) |
| `TELEGRAM_BOT_TOKEN` | @BotFather |
| `TELEGRAM_WEBHOOK_SECRET` | придумывается самостоятельно, проверяется в вебхуке |

Ключей в коде нет — всё читается из переменных окружения.

### Дополнительные миграции

Помимо `schema.sql` выполнялись:

```sql
-- политики доступа к файловому хранилищу
create policy "authenticated can upload chat files"
on storage.objects for insert to authenticated
with check (bucket_id = 'chat-files');

create policy "anyone can read chat files"
on storage.objects for select using (bucket_id = 'chat-files');

create policy "service role full access chat files"
on storage.objects for all to service_role
using (bucket_id = 'chat-files') with check (bucket_id = 'chat-files');

-- пересылка сообщений
alter table messages add column if not exists is_forwarded boolean not null default false;
alter table messages add column if not exists forwarded_from text;

-- шаблоны с переменными
alter table canned_replies add column if not exists has_variables boolean not null default false;
```

### Пояснение по пункту 16 (голосовые)

Запись через микрофон в панели работает, файл доходит до клиента и **прослушивается**, но приходит
как аудиофайл, а не как нативное голосовое сообщение Telegram (без характерной полоски записи).

Причина: Telegram для метода `sendVoice` ожидает формат OGG/OPUS. Safari, в котором велась
разработка, пишет через `MediaRecorder` в `audio/mp4` (m4a) — OGG он не поддерживает.
В коде реализован выбор наиболее подходящего из доступных форматов, но привести m4a к OGG
без конвертации невозможно.

Чтобы закрыть пункт полностью, нужна конвертация — либо в браузере через ffmpeg.wasm
(около 30 МБ, заметно утяжеляет загрузку), либо на сервере. От этого решения отказался
сознательно: ради одного дополнительного пункта тянуть тяжёлую зависимость в проект
показалось неоправданным.

## 4. Обработка ошибок

- **Сообщение не отправилось** — запись создаётся до вызова Telegram API со статусом «отправка»,
  при ошибке статус меняется на «не отправлено» с текстом причины прямо под сообщением.
  Молча сообщение не теряется.
- **Клиент заблокировал бота** — распознаётся по ответу Telegram, диалог помечается флагом,
  вверху переписки появляется предупреждение.
- **Файл слишком большой** — проверка при выборе файла, до загрузки. Сотрудник видит имя файла,
  его размер и лимит.
- **HEIC** — конвертируется в JPEG в браузере; если браузер не смог прочитать формат,
  показывается предупреждение, но отправка не блокируется.
- **Ошибка записи в базу** — результат вставки проверяется, а не только факт отправки в Telegram.

## 5. Что оказалось сложнее всего

**Напоминания.** Дольше всего провозился именно с ними, причём проблема оказалась не одна,
а три подряд, и каждая маскировала следующую:

1. Сначала напоминания не срабатывали вовсе. Проверил через SQL напрямую — записи в базе
   были, значит сохранение работает.
2. Оказалось, поле `datetime-local` в браузере отдаёт время без часового пояса, и на сервере
   оно трактовалось как UTC. При разнице с Бишкеком в 6 часов напоминание «срабатывало»
   на 6 часов позже. Исправил переводом в ISO с учётом зоны браузера.
3. После исправления всё равно ничего не появлялось — оказалось, браузер держал закэшированную
   версию страницы. Помогло жёсткое обновление. Из-за этого я какое-то время чинил уже
   починенное, не понимая, почему нет эффекта.

Вывод, который вынес: когда что-то не работает, нужно сначала определить, на каком именно
участке цепочки теряются данные (браузер → API → база), а не править наугад. Прямой запрос
к базе и обращение к API по URL в браузере сэкономили бы мне час.

**Второе по сложности — скорость.** Панель заметно подтормаживала на каждое нажатие. Причина
оказалась в географии: база данных в Сингапуре, а серверные функции Vercel по умолчанию
разворачиваются в США. Каждый запрос летел через полмира дважды. Решилось файлом `vercel.json`
с указанием региона `sin1` — после этого разница ощущалась сразу.

## 6. Что доделал бы при наличии ещё недели

**Голосовые сообщения — в первую очередь.** Довёл бы до настоящего voice в Telegram через
конвертацию в OGG/OPUS. Скорее всего делал бы конвертацию на сервере, а не в браузере,
чтобы не утяжелять загрузку панели для сотрудников.

Кроме этого:

- **Пересылка через выпадающий список.** Сейчас сотрудник вводит имя клиента вручную в диалоговом
  окне браузера — рабочее, но неудобное решение. Нужен нормальный выбор из списка с поиском.
- **Правка сообщений без `prompt()`.** Та же история: сейчас используется стандартное окно браузера,
  правильнее — редактирование прямо в переписке.
- **Восстановление соединения.** Заметил, что при обрыве связи или после деплоя открытая вкладка
  перестаёт получать обновления в реальном времени до перезагрузки страницы. Нужно отслеживать
  состояние соединения и переподключаться автоматически, а сотруднику показывать индикатор.
- **Уведомления о новых сообщениях** — звук или системное уведомление, когда вкладка неактивна.
  Без этого сотрудник может не заметить обращение.
- **Тесты.** Сейчас проверка полностью ручная. Для проекта, который будет развиваться,
  нужны хотя бы тесты на приём вебхука и отправку сообщений.

## 7. Известные ограничения

- Голосовые из панели приходят аудиофайлом, а не нативным голосовым (см. пункт 16)
- Редактирование сообщений с вложениями невозможно — это ограничение Telegram API,
  редактировать можно только текстовые сообщения бота
- Удаление сообщения у клиента работает только в течение 48 часов — ограничение Telegram,
  по истечении срока сотрудник получает понятное объяснение
- Панель проверялась в Safari и Chrome на macOS; на мобильных устройствах открывается,
  но интерфейс не адаптировался специально
